6. QUEUE / PLAYBACK CONTRACT PENTING
======================================================================

Queue adalah source-scoped active playback session.

Saat user memilih media dari source A:

source A
→ setQueue(A)

Kemudian memilih source B:

source B
→ setQueue(B)

Queue A tidak otomatis diappend ke Queue B.

Cross-source mixing hanya boleh terjadi melalui future explicit action seperti:

append()
insertNext()

Queue snapshot tidak diam-diam mengikuti filesystem setelah playback dimulai.

Retained QueueState PHASE 15:
- in-memory
- dapat bertahan setelah runtime playback dihentikan
- bukan persistent History

Perbedaan penting:

stopPlayback()
→ stop runtime playback
→ retain QueueState

clear()
→ stop runtime playback
→ clear QueueState

CRITICAL CONTRACT:

QueuePlaybackCoordinator.clear()

harus melakukan:

playbackEngine.stop()
↓
queueEngine.clear()

Jangan dibalik.

Pernah ada crash/race terkait stale playback state.

Stale ENDED callback:
harus diabaikan ketika playback media sudah tidak sama dengan
canonical current queue item.

7. PLAYLIST PRODUCT CONTRACT
======================================================================

Playlist:
persistent user-owned media collection.

Queue:
temporary active playback session.

Playlist ≠ Queue.

Persistence:
Room.

Playlist storage:
media-agnostic.

Playlist presentation:
AUDIO-FIRST.

Ini deliberate NexPlay product behavior.

Audio-only playlist:

[A1, A2, A3]
→ Audio Player

Video-only playlist:

[V1, V2, V3]
→ Audio Player
→ audio track video dimainkan sebagai audio presentation

Mixed playlist:

[A1, V1, A2, V2]
→ tetap Audio Player continuously

PENTING:

VideoItem tetap canonical VideoItem.

Jangan:
VideoItem → AudioItem conversion

Queue tetap boleh menyimpan mixed MediaItem.

PlaylistContext harus tetap dipertahankan.

Jika current Playlist item adalah VideoItem:
user dapat memilih "Switch to Video".

Explicit Switch to Video:

- tidak rebuild queue
- tidak mengganti media identity
- tidak mengganti PlaylistContext
- tidak membuat playback runtime baru

Ketika current playlist item berubah setelah explicit video presentation:

→ kembali ke Audio Player

Policy ini HANYA berlaku untuk PlaylistContext.

Direct Folder/Search playback tetap type-correct:

Folder/Search AudioItem
→ Audio Player

Folder/Search VideoItem
→ Video Player

13. PLAYLIST DRAG REORDER — CURRENT CONTRACT
======================================================================

Flutter NexPlay dan cromaguy/Rhythm pernah dipelajari sebagai behavior

PENTING:
Source Rhythm tidak boleh dicopy verbatim.

NexPlay menggunakan implementation sendiri.

Current interaction architecture:

pointer input
    ↓
update drag position
    ↓
frame-driven processing
    ↓
calculate dragged card position
    ↓
read live LazyColumn slot
    ↓
determine reorder
    ↓
edge auto-scroll
    ↓
logical displayedItems update
    ↓
release
    ↓
settle
    ↓
persist final reorder ONCE

Tujuan utama:

Dragged row harus terasa tetap menempel pada jari.

Underlying list boleh berubah index tanpa membuat dragged row melompat.

Room tidak ditulis setiap frame.

Persistence hanya dilakukan ketika final drop.

Important bug yang pernah ada:

Initial:

A

Sebelumnya:
tidak responsif.

Root cause yang ditemukan:
pointerInput keyed hanya pada mediaUri dapat mempertahankan coroutine
lama dengan lambda onDragStart yang menangkap stale item index.

Fix:

rememberUpdatedState digunakan untuk current callbacks:

- onDragStart
- onDrag
- onDragEnd
- onDragCancel

pointerInput tetap stable, tetapi callback selalu terbaru.

Jangan mengganti secara sembarangan dengan:

dapat me-restart pointer coroutine / membatalkan active gesture.

Manual patch harus menggunakan format:

FILE:
<path>

CARI:
<actual exact block>

GANTI MENJADI:
<full replacement>

EFEK:
<short explanation>

Rules CARI:

- persis current source
- lengkap untuk Ctrl+F
- preserve indentation
- tanpa ellipsis

Rules GANTI MENJADI:

- complete
- paste-ready
- smallest sufficient change

Jangan:

- pseudo-code sebagai actual patch
- generic patch
- guessed source
- guessed path

30. LESSON DARI ACCIDENTAL DOUBLE CLOSEOUT
======================================================================

Closeout command sebelumnya sempat dijalankan dua kali.

Run pertama:
benar.

Run kedua:
sebagian Replace-Required gagal karena original source text sudah berubah,
tetapi beberapa insertion masih berhasil sehingga duplicate docs muncul.

Accidental run menghasilkan:

1c642d6

Sudah direvert dengan:

9efdc6a

Pelajaran untuk command docs berikutnya:

- sebisa mungkin buat command idempotent;
- cek apakah target checkpoint sudah ada;
- jangan melakukan insertion kalau target state sudah tercapai;
- validate seluruh required old-state sebelum menulis file bila memungkinkan;
- fail-fast sebelum Write-Lf;
- setelah PowerShell throw, jangan terus mengeksekusi sisa block manual;
- setelah command sudah commit + push sukses, jangan jalankan ulang
  command yang sama;
- kalau accidental duplicate terjadi lagi, cek actual Git state dulu;
- jangan otomatis reset/rebase/force-push.
